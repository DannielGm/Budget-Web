# Budget keeper — Laravel + React Migration Fork

Project: `E:\Projects\Budget-Web`

Laravel 11, SQLite, React (Inertia.js), and Tailwind CSS. This is a web-based migration of the Budget Android app, designed for cross-platform availability while maintaining the authoritative financial logic and "Single Screen" UX. Packaged natively for Android using NativePHP.

## Implemented Features

- **Core Logic Parity**: Ported the complex financial formulas (Cash vs. Credit, Debt calculation, True Budget) from Kotlin to PHP.
- **Carry-forward Engine**: Automated rollover of closing balances and unpaid debt between months.
- **Web Dashboard**: Responsive React-based UI that replicates the Android dashboard structure.
- **Interactive Graphing**: Multi-metric visual budget tracking powered by Recharts, showing Available Balance, Expenses, and Savings movements over time.
- **Persistent Storage**: Backed by a clean SQLite schema with Eloquent models for Budgets, Categories, Expenses, Debts, and Savings.
- **Savings Integrations**: Native tracking for Binance, Bank, and Physical savings with real-time BCV conversion.
- **Theme Toggle**: Full support for Light and Dark modes with theme-aware chart colors.
- **Análisis**: A month-health screen reached from the dashboard summary strip, deriving every figure from props the dashboard already has (no second endpoint, no second source of truth).
- **Touch Feedback**: Short press haptics on every `.touch-feedback` control, wired through one delegated listener.
- **Display Currency**: Every figure can be read in dollars or euros. A rate picked from a specific day uses that day's real BCV euro rate; a custom rate is reused as typed and only the symbol changes. The rate history shows whichever series is on screen with the other one beside it as a comparison line.
- **`income_rate` is the month's rate, full stop**: it is whatever the budget form holds — a custom number the user typed, or the BCV figure `refreshMonthRates()` kept in step — and it is what every bolivar figure on screen converts at. `refreshMonthRates()` re-derives it from the active series on every load and never touches an `is_custom_rate: true` budget, so "the form wins" needs no extra enforcement. The payload exposes it as `rates.effective`; the two real BCV series survive as `rates.{usd,eur}.latest` (the form's daily switch, and what a savings pot is valued at) and as `rates.{usd,eur}.day` for a day filter.
- **Savings come in two pots**: a pool is not marked as one currency. Every savings movement carries the currency it was saved in — `USD` or `EUR`, defaulting to USD, which is what every row written before the column existed was — and a pool therefore reports `balance_usd` and `balance_eur` separately. A screen states the pot its own currency is saved in: dollar mode shows the dollars, euro mode the euros, and the pot on screen is never converted: its figure is the amount as stated, and its bolivar line is the app's own rate for the day or range, the one every other bolivar figure on screen divides by. `amount_usd` holds the amount *in that currency* and keeps its historical name, because renaming it would make the backup importer strip the amount out of every file already on a device.
- **Only two places add the pots up**: the pool strip and the `/savings` summary. Both leave the pot already in the display currency exactly as it is and convert only the other one, pairing the two BCV series from the same day: a conversion taken from today's rate on one side and a picked day's rate on the other is not a number the user can check. The summary also sums every source into one patrimony figure: cash + both pots − named debts − this month's credit purchases. A pot whose series has not loaded is left out of a total rather than valued at the other currency's rate.
- **A savings movement says which pot it belongs to**: `SavingsForm` and `TransferModal` offer the choice, defaulting to the currency on screen, and the amount label, the rate label and the rate default all follow it. Neither takes its rate from the caller, which in euro mode pre-filled a euro rate into a dollar field and wrote a bolivar amount roughly twenty percent high; a rate the user typed survives a currency change. A movement is priced at today's real rate even while a past day is on screen, because it is stamped now. The summary's back control returns to the savings view rather than the balance card, because the view travels in the URL (?view=).
- **A committed swipe eats the click it causes**: the pool strip is one large link, so a drag that changes view also fired a click and opened the summary instead. `useSwipeViews` arms a one-shot capture listener on `window` for that click only, and disarms itself if none arrives, because a listener left armed would eat the next deliberate tap. The rule lives in an exported `createClickSwallower(target)` so it is testable without a DOM.
- **The currency switch is in the header**: a savings screen states one pot, so answering "what are my euros worth in dollars?" used to mean Settings -> toggle -> reload -> swipe -> strip. The header switch writes the preference through the one exported `setDisplayCurrency` Settings also calls, so the two controls cannot write it differently, and it is labelled with the currency it moves TO. Every money figure measures itself with `useFitText`, which is why a six-figure pool, cash balance or patrimony gives way instead of pushing past the card.
- **A new expense starts at the rate the balance card is using**: `ExpenseForm` has always taken a `defaultRate`; the dashboard simply never passed it, so every new expense opened with a rate of 0,00. It is fed `contextRate`, which is already the day's rate when a day filter is active and the month's otherwise, and it stays editable. A day picked in the form's own calendar re-reads that day's rate from `exchange-rate/history`, but only while the field still holds the rate the form filled in -- a custom rate the user typed is never overwritten.
- **Long rate ranges are honest about what is stored**: `1A` and `Todo` showed a truncated window because the archive that fills them is a bulk download, and it was being given the same two-second budget as the daily rate -- which a history of thousands of entries never fits inside. Bulk calls get their own budget, the archive is pulled by the refresh button rather than by the request that has to draw the chart, and the chart states the span it really has. `ensureFresh` only backfills history after a fetch that actually succeeded, so a cold start with no connection costs the daily timeout and no more.
- **Back closes what is open**: a hardware or gesture back in a WebView is a history navigation, not a key event, so menus, dialogs and dropdowns never saw it and the app navigated away underneath them. `useDismissOnBackButton` stands a sentinel history entry while a layer is open; back pops it and closes the layer instead. It is wired into `Modal` (every dialog in the app), `Dropdown` and the dashboard's view menu, and it re-arms the sentinel so back keeps closing rather than escaping on the second press.
- **JavaScript Test Suite**: Vitest covers the pure money, rate and range logic that the PHP suite cannot reach, and renders components in both display currencies to prove they state one savings pot and do not throw at render.
`database/data/september.private.json` contains real financial data and is **not encrypted**. It is Git-ignored now and no longer tracked, but it was committed in the initial commit (`420b5a18`) before the ignore rule existed, so **it is still recoverable from the repository's history and from any existing clone**. Treat that data as exposed: anything genuinely sensitive in it should be rotated or moved, not merely untracked. The local SQLite database (`database/database.sqlite`) stores all sensitive information. Ensure this environment is kept private and secure.

### alpha 0.4.0 — Remote Desktop

- **Temporary LAN Editing**: Added an Android-only **Escritorio remoto** option to the settings menu. When activated, the APK exposes the same embedded Laravel application to a computer on the local Wi-Fi network, allowing budgets, expenses, debts, savings, transfers, and settings to be edited from either device against the phone's single SQLite database.
- **NativePHP Plugin**: Added the local `budget-web/nativephp-remote-desktop` plugin with `RemoteDesktop.Start`, `RemoteDesktop.Status`, and `RemoteDesktop.Stop` Android bridge functions. The plugin starts a Kotlin `ServerSocket` on the Wi-Fi interface (port `8080` by default), detects the phone's LAN IPv4 address, serves Vite/static assets, and forwards dynamic HTTP requests into NativePHP's persistent embedded PHP runtime.
- **Pairing Flow**: The phone displays a local URL and temporary pairing code. A computer opens the URL, enters the code, receives an HttpOnly remote-session cookie, and can then use the complete BKeeper web interface. QR-code pairing is intentionally deferred to a later release.
- **Automatic Shutdown**: Remote access expires automatically after 15 minutes by default, with a visible countdown and an immediate **Desconectar escritorio** action. Sessions, pairing state, and the listening socket are cleared when the server stops.
- **Isolated Browser State**: LAN requests use an explicit cookie header, keeping the computer's Laravel session separate from the phone WebView's cookie jar while still using the same application database and PHP execution lane.
- **Security Boundaries**: Management routes such as `/remote-desktop/status`, `/start`, and `/stop` are blocked from remote LAN clients, preventing a paired computer from retrieving the pairing token or controlling the listener. Request bodies are size-limited, and the feature is intended only for trusted local networks.
- **Device Gating**: The settings option appears only when NativePHP reports an Android runtime with the compiled `RemoteDesktop.Start` bridge function. Web and unsupported platforms do not expose the feature.
- **Backend and UI**: Added `RemoteDesktopManager`, `RemoteDesktopController`, start/status/stop routes, native capability detection, and a centered mobile settings panel with activation, address/code copy actions, expiration countdown, errors, and disconnect controls.
- **Android Build Requirement**: The feature compiles against Android API 26+ and requires Java 17 or newer for the Android Gradle Plugin. The project was validated with the installed Java 21 runtime (`C:\Users\DANIE\.jdks\jbr-21.0.11`).
- **Validation**: NativePHP plugin validation, Android Kotlin compilation (`compileDebugKotlin`), the production Vite build, and the Laravel test suite all passed. Physical-device LAN testing remains necessary to verify router/client isolation and foreground Android behavior.
- **Security Limitation**: The current implementation uses local HTTP and is not intended for public-internet exposure. A production-grade remote service would require TLS, durable user authentication, device pairing/revocation, and optimistic-lock conflict handling for simultaneous phone/PC edits.

### alpha 0.4.1 — Remote Desktop White-Screen Fix & Reproducible Android Patches

- **Root Cause of the White Screen**: After pairing, the computer loaded a blank page. `serveStatic()` only served paths under `build/`, `_assets/`, and `storage/`, so the Blade shell's Vite asset requests fell through to the PHP dispatcher and were answered with application HTML using a JavaScript MIME type. The browser refused the script, React never mounted, and the page stayed white. Pairing itself is pure Kotlin, which is why the code exchange appeared to work.
- **Asset Resolution Rewritten**: `serveStatic()` now mirrors the phone WebView's own resolution strategy — the requested path first, then `vendor/`, then `build/` — instead of a prefix allow-list. Added correct MIME types (`js`/`mjs`, `css`, `json`, `svg`, `png`, `webp`, `gif`, `ico`, `woff`/`woff2`/`ttf`/`eot`, `html`, `txt`), `Cache-Control`, and `Access-Control-Allow-Origin: *` for fonts. Path traversal remains blocked through canonical-path containment.
- **HTTP Response Hardening**: `writeRawResponse()` now detects the header/body separator (`\r\n\r\n` or `\n\n`), preserves an existing `HTTP/` status line or synthesizes one, strips `Content-Length`/`Transfer-Encoding`, and guarantees a `Content-Type` default so HTML always parses. (Note: it claimed to re-compute the length against the *rewritten* body. It did not — see the 0.4.4 entry for the bug that actually caused it.)
- **Origin and Cookie Re-Hosting**: Both `http://` and `https://127.0.0.1` are rewritten to the LAN origin in the response body, in `Location`, and in `Set-Cookie`. `Domain` and `Secure` attributes are stripped from cookies so the computer's browser retains a valid Laravel session over plain HTTP — previously a `Secure` cookie would have been silently discarded. (This rewrite was intended to fix the origin problem; it did not. See 0.4.4.)
- **Correct Status Lines**: Added a reason-phrase table. The server previously emitted invalid lines such as `HTTP/1.1 303 OK` and `404 OK`; the pairing redirect is now a proper `303 See Other`.
- **Visible Failures**: A blank upstream response now returns a styled `502` page naming the failing method and path, instead of silently producing empty output. Future regressions will be diagnosable from the browser.
- **Reproducible Android Patches**: The remote desktop depends on three edits to Kotlin files inside the generated `nativephp/android` scaffold, which `php artisan native:install` and the plugin compiler both regenerate. The edits live in one place — `Support\AndroidBridgePatches` — and are applied by a `post_compile` plugin hook, so `php artisan native:build android` alone produces a correct APK:
  1. `PHPBridge.handleLaravelRequest()` gains an overload accepting an explicit `Cookie` header, so a LAN client keeps its own session instead of being merged into — or overwriting — the phone's cookie store.
  2. `MainActivity.phpBridge` is made public so plugin bridge functions can dispatch into the same persistent PHP runtime.
  3. `ShareFunctions` learns that `.json` is `application/json`, so a backup handed to the share sheet is not offered as the `*/*` catch-all.
- **Why a hook rather than a manual step**: the three targets are perishable at *two different points*. `PHPBridge.kt` and `MainActivity.kt` live in `src/main/java` and are reset by `native:install`; `ShareFunctions.kt` lives in `app/src/nativephp/kotlin` and does not exist until the plugin compiler has run (`AndroidPluginCompiler` deletes and re-copies that whole tree on every build). There is therefore no single point at which a human can patch all three by hand. `post_compile` fires after the plugin tree is generated and before Gradle runs, which covers all three in one pass.
- **Patch Design**: matching is regex-based and line-ending aware (the scaffold uses CRLF on Windows), and each patch declares a marker substring present only once applied, so re-running is a safe no-op. Each patch also declares a `min_matches`/`max_matches` band and **every** match is rewritten, not just the first: patching one of several identical sites would otherwise report success while leaving the rest unfixed, shipping a half-patched APK. If the NativePHP template changes and the match count falls outside the declared band, the patch fails rather than applying a partial edit. Every write is preceded by a `.prepatch` snapshot of the original file, so a bad anchor is diffable and recoverable.
- **A failed patch is loud but NOT fatal**: `PluginHookRunner::runPluginHook()` (vendor) downgrades a non-zero exit code to a warning and proceeds to Gradle. The hook command therefore cannot abort the build, and its output says so explicitly rather than implying the build was stopped. Treat a `[FAILED]` line in the build log as *do not install this APK* — the remote desktop will be broken.
- **The LAN re-host fix is not a patch**: it lives in the plugin's own `resources/android/RemoteDesktopServer.kt`, which the compiler copies in on every build, so it needs no patching. The hook only *asserts* it is present, so a regression in the source is caught rather than shipped. Patching it as well would be a second competing edit whose marker would report success by "fixing" a file the source had already fixed.
- **Manual escape hatch**: `php packages/nativephp-remote-desktop/patch-android.php [--check]` still applies or reports the same patches, delegating to the shared class rather than duplicating it. `--check` exits non-zero when anything is missing, making it usable as a CI or pre-build guard.
- **Validation**: the cycle was verified from a pristine vendor baseline — files restored, patches applied from scratch, re-run as a no-op, and `--check` clean. The generated Kotlin was inspected to confirm indentation survived the patch, which is what broke the build when the replacement text was a heredoc.

### alpha 0.4.4 — Remote Desktop Origin & Pairing Hardening

- **White screen root cause**: `writeRawResponse()` converted the body to bytes *before* running the re-host rewrite, so the rewritten string was thrown away and the original bytes were sent.
- **Laravel generates the right URLs**: `HandleRemoteDesktopOrigin` (prepended to the `web` group) reads the `X-Remote-Desktop-Origin` header the server sets and rebinds `URL::useOrigin()`, `URL::useAssetOrigin()` and the Vite asset resolver for that one request. `@vite` preloads, scripts, dynamic imports, Ziggy and Inertia's payload then all emit LAN URLs natively, with no `127.0.0.1` in the output. Response rewriting is now only a backstop. (`useAssetOrigin()` is required because NativePHP sets `ASSET_URL` to `127.0.0.1` in C before boot, and that value beats the request root in `asset()`.)
- **No `trustProxies()`**: the middleware binds the origin itself, so trusting every peer is unnecessary and would let any `X-Forwarded-*` rewrite it. The suite passes without it. Overrides are wrapped in `try`/`finally` because NativePHP keeps one warm PHP interpreter, where a leaked `forcedRoot` would mislabel every later page.
- **Pairing**: only a SHA-256 digest is stored and compared with `MessageDigest.isEqual()` (constant time) rather than plaintext `==`; 5 failed attempts trigger a 15-minute per-IP lockout (`429`); pairing replaces any existing session; and the TTL is checked on every connection, so a paused tab cannot outlive the window (`410 Gone`). `/remote-desktop/*` and `/backup/import/pick` return `404` to remote clients — the document picker opens a native dialog with no remote counterpart.
- **Verification**: PHP is covered by tests (108 passing, 1 pre-existing skip). **The Kotlin has not been compiled** — no Android build has run against these changes, so device behaviour is unconfirmed.

### alpha 0.4.5 — Dashboard UI Tightening, Análisis & Touch Fixes

- **One owner for the month figures**: the Balance card no longer repeats `Ingresos` / `Gastos`; `MonthSummaryStrip` is the single surface for them, and the card keeps only the headline balance, the BCV rate and `Editar ingresos`. The dashboard was previously showing two differently-sourced numbers under the same "Gastos" label at the same time.
- **`Gastos` now means one thing**: the strip was summing `visibleCategories`, which honours the 7d/1d range filter, so it disagreed with both the balance card and the graph. It now calls the shared `calculateCashExpenses(budget, dateFilter)` helper, so all three surfaces render the same figure. `Pagado` is unchanged and remains a month-scoped total.
- **Balance figure matches the other dashboard heroes**: the preferred size is 48px, the same as `SavingsDashboard` (`text-5xl`), and the element carries that class outright, so 48px is what renders unless the value would genuinely overflow. `useFitText` only runs its search when the value clips, and now re-measures once webfonts finish loading — the first measurement was taken against fallback glyphs, which is why the number had been settling smaller than it should. A long figure steps down to 30px, and `clipped` is exposed so one too long even for the floor drops once more to 22px instead of losing digits.
- **Savings tiles and movement rows never truncate**: the pool `≈ Bs` line, the movement-type tag and each movement’s `Bs/$` line now run through `useFitText` and stay on one line, shrinking to fit rather than clipping. The pool tiles and row fragments had to become real components (`PoolTile`, `MovementTag`, `BsRateLine`) because the fit search is a hook and cannot be called from a `.map` callback. Pool tiles were also widened with `-mx-1` so they fill the card better, leaving the `gap-2` spacing between them untouched. Each keeps its original `text-[10px]` as the baseline, so the fit search only ever shrinks from the size it had before. In the history each movement stacks as concept name, then the movement-type tag, then the date, so the tag never shares a row with the amount and the amount column stays `shrink-0` regardless. The tag is capped at 7px and given a full row of its own.
- **Debt form "Estado actual" panel readable in dark mode**: the row labels used `text-gray-500` with no `dark:` variant, and the amounts carried no colour at all, so the panel inherited the modal foreground and its labels sat below comfortable contrast on the dark surface. Every value is now explicitly themed (`dark:text-white` for the figures, `dark:text-red-400` for new charges, `dark:text-gray-300` for labels, `dark:text-gray-400` for the USD sub-line), matching the treatment the same panel already had in `DebtSummaryModal`.
- **Clear actions consolidated into Settings**: the dashboard menu and the Settings storage card both offered deletes, with different wording and different reach — the menu could only clear whichever month happened to be open, and hid the day action behind the day already selected. The menu now offers only `Llenar datos de prueba` (kept there deliberately, as a dev action) plus the normal navigation, and `StorageCard` owns all three deletes: a new **Borrar un día** field opening the existing `BudgetCalendar` in `pickDay` mode, where the day derives its own month so the two can never disagree, alongside the existing month picker and **Borrar Todo**. Each confirm dialog now states precisely what survives — the month and its categories, and the exchange rates — and a standing note records that BCV rates are never deleted. The Settings header also gained a back-to-dashboard button using the same `header-icon-button` control as the dashboard header.
- **Settings clear actions now do what they promise, and never touch exchange rates**: `Limpiar datos del día` was calling `settings.clear-day`, a route that was never registered, so `route()` threw and the button had never worked; the route and controller action now exist and delegate to the already-correct `BudgetService::clearDay()`. `Limpiar mes actual` previously deleted the month and its categories outright and never touched transfers or debt payments; it now clears the movements while keeping the month and its categories in the list with the budget row zeroed. `Limpiar todos los datos` used `truncate()`, which on SQLite resets AUTOINCREMENT and relaxes foreign-key enforcement, and it omitted the `transfers` table entirely; it now uses `delete()` across all seven tables, children before parents, with no reliance on cascade. All three leave `exchange_rates` untouched, and `ClearDataTest` asserts that for each one, along with cross-month isolation and rejection of a day outside the requested month.
- **BCV history defaults to 1M with a permanent 30D figure**: the rate view now opens on `1M` instead of `6M`, and the hero always carries a 30-day percentage. Because the shorter default range cannot supply a full 30-day lookback, the badge falls back to the oldest point available and is marked with a `*` plus a footnote, so the number is never silently wrong. The chart is a hand-rolled SVG whose axis labels were 9px inside a fixed `viewBox`; they are now 14px with the padding increased to make room, otherwise the larger text would have been clipped at the plot edge. `Historial diario` is now just `Historial`, and it surfaces forward-published rates: the series window previously stopped at today, so a BCV rate published for an upcoming day could never appear, so the endpoint now extends one day past today and those rows are tinted and marked `fut` in the date view. Compact dates append the year only when it is not the current one, which keeps a year boundary (`28 dic` / `02 ene`) unambiguous without making every row longer.
- **Tightened the other two hero cards**: on the Savings and BCV cards the title row is sized by its button (32–36px) while the title is only ~15–20px, and `items-start` left the remainder as dead space beneath the title, with `mb-4`/`mb-3` adding more. The rows are now `items-center` with a tighter bottom margin, so the amount sits directly under its title on both.
- **Rate badge shares the `$` line**: the rate pill, error dot and refresh button sat on an `items-end` row, which pinned the pill bottom to the glyph baseline and made it look like it was floating. The row is now `items-center`, so the `$` equivalent and the rate controls sit on one optical line despite their very different sizes.
- **Summary strip dividers strengthened**: `divide-gray-100/800` was effectively invisible; now `divide-x-2 divide-gray-200 dark:divide-gray-700`, with `px-5 py-4` and per-column padding so no figure sits flush against a rule.
- **Graph header**: the `Presupuesto cubierto` / `excedido` badge now sits on the same line as the metric title, right-aligned. It shares the row with the *title* only — the amount keeps its own full-width line beneath, so the badge can no longer squeeze the figure as it did before.
- **`Tasa Diaria BCV` is now a checkbox, and it means what it says**: replaced the custom switch (whose active state was bound to `!is_custom_rate`, so it lit up exactly when the rate was automatic) with a native checkbox matching the `additiveIncome` control beside it. Checked = use the latest daily BCV rate; unchecked = the typed value is a custom rate, and it is kept. Checking pulls in the live rate (or `0` when none is available); typing a rate or picking a date from the calendar unchecks it, so the box always reflects what the field actually holds.

- **`Ánálisis` is a destination of its own, opened by the summary strip**: pressing the strip's three figures navigates to `/insights`, and the panel grows out of the strip through a shared framer `layoutId="insights-panel"`, so the two screens read as one continuous surface. It is a real route rather than a fourth swipe view because it needs its own URL, its own back control, and the month/day it was opened on. The payload is shared with the dashboard through one private `BudgetPayload()` builder in `BudgetController`, so the two screens cannot disagree about a figure — `InsightsRouteTest` asserts that directly by comparing the two responses. The strip stays a real `<a href>`, so middle-click and open-in-new-tab still work.
- **Every figure is derived, never duplicated**: `resources/js/lib/insights.js` holds `buildInsights()`, pure functions alongside the existing `budgetExpenses.js` / `debtMath.js`, so the arithmetic is testable without mounting React. Cash spend reuses the `cash_expense && !is_presupuesto` rule the balance card already uses. `daysElapsed()` is what makes the burn rate honest: it counts *today* for the running month, so the rate is live, and the full month for a past one, which collapses the projection onto the real total instead of extrapolating from stale data.
- **Ánálisis figures that looked right and were not** — four of them, each a case of the code being correct and the answer still wrong:
  · The hero’s `useFitText` bounds were `{ min: 22, max: 44 }` against the balance card’s `{ min: 30, max: 48, emergencyMin: 22 }`, so the two heroes never matched. They now share the card’s parameters and its `text-5xl` baseline.
  · `Gasto de presupuesto` divided each category by the plan total, which is **100% by construction** whenever a month has one plan category — a number that cannot mean anything. It now reports plan against `available_balance_bs` using the same `available >= plan` rule the dashboard’s `isBudgetOk` already applies, and the per-category shares stay plain labels. A zero available balance stays neutral rather than warning, since there is nothing to compare against.
  · The savings rate counted only `kind === 'transaction' && type === 'deposit'`, so money moved into a pool as a **transfer** was silently dropped and the rate read 0% for anyone who funds savings that way. Flow is now counted by direction, mirroring the rule the balance graph already uses.
  · Presupuesto expenses were tagged `Gasto` in the activity feed, because the tone map had no entry for them and they fell through to the default. They now carry the same indigo `Presupuesto` badge the expense card already uses.
- **The balance graph can be touched again**: `drag="x"` on the view wrapper made framer's drag compete with the chart's own `onTouchMove` for every horizontal gesture, so the graph could not be inspected on touch at all. The wrapper is now a plain `touchAction: 'pan-y'` surface and the swipe lives in `useSwipeViews`, which measures the gesture instead of animating it. The view no longer moves under the finger at any point — it changes on release, which is what a swipe between screens is supposed to feel like. An axis lock claims the gesture only once it is clearly horizontal, so vertical scrolling stays native, and pointers starting on form controls are ignored outright.
- **The swipe threshold was backwards in both directions**: the old rule was `Math.abs(offset.x) * velocity.x > 10000`, so a 20px twitch at 500px/s committed as a swipe while a slow, deliberate 200px drag was rejected. Distance now decides — `>= 140px` alone commits, or `>= 60px` at `>= 300px/s`, or a `>= 30px` flick at `>= 800px/s` — and the old arithmetic is pinned by cases in both directions so it cannot come back.
- **Press feedback on every control**: `useHapticFeedback` adds a 10ms `navigator.vibrate` on press for anything inside `.touch-feedback`, through a single delegated `pointerdown` listener on `document`. The class is already the app-wide convention for "this responds to touch" (26 elements), so the feedback required no changes at any call site and any new control that follows the convention gets it for free. It skips disabled elements, respects `prefers-reduced-motion`, and swallows the error some browsers throw when `vibrate` exists but the page is not yet user-activated.
- **No JS test runner**: the threshold logic was verified against 14 cases and then the harness was removed. `package.json` has no `test` script and neither vitest nor jest is installed, so standing tests up was a toolchain decision left to the maintainer rather than something added uninvited.

### alpha 0.5.0 — Euro Display Currency, Test Suite & Truthful Filtering

- **Every figure can be read in dollars or euros**, switched from Settings. `exchange_rates` became currency-scoped, keyed by `(date_iso, currency)`, with the euro series fetched from the same `dolarapi.com` endpoints already used for dollars — one URL template with a currency segment rather than a second implementation that could drift. Every pre-existing row migrated to `USD`, so the 898-row dollar archive survived untouched and needed no re-fetch. Each query method takes an optional currency defaulting to `USD`, which means every existing caller keeps its exact behaviour; a test asserts that explicitly for the month rate, the day rate and the series.
- **The two rate rules live in one tested function.** A rate picked from a specific day uses that day's published rate *for the currency on screen*, so a euro figure is a real historical euro rate. A custom rate is the number the user typed, applied verbatim with only the symbol changed — the euro sign is a presentation choice, not a claim the figure was an official euro rate. Both currencies run the same path; an early version special-cased dollars to ignore the day filter, which would have made a euro day view and a dollar day view disagree for identical data, and the test caught it.
- **Savings are stored in dollars, so euros need a cross rate.** 
- **The preference is a display setting, not a stored one**, on the same `localStorage` convention the theme already uses, because the app allows signed-out use and a per-account column would have nowhere to live for a guest. A pre-paint script in `app.blade.php` sets it before React mounts, so the first paint already carries the right symbol.
- **`lib/money.js` was split rather than grown.** Formatting stays pure in `money.js`; the currency context and the pure conversions live in `lib/currency.jsx`; `hooks/useFigure.jsx` bridges a stored figure to the one the user reads. A component that only needs a number never pulls in a context.
- **Two guards now stand where nothing stood before.** `useCurrencyGuard.test.js` fails if any component hard-codes a dollar sign, and if a currency value is rendered by a component that does not bind it. The second guard exists because that mistake ships a white screen: a value bound in one component is not in scope in a sibling, the code is valid, the pure helpers are correct, and neither the build nor the unit tests can see it. It was proven by re-injecting the fault.
- **A JS test suite exists.** `npm test` runs 225 Vitest assertions over the pure logic the PHP suite cannot reach: the swipe threshold, the day-range rules, the debt and savings arithmetic, the insights derivations, the graph/hero reconciliation, and the currency rules. Getting there needed two corrections — `npm install` fails on a **pre-existing** peer conflict (`@vitejs/plugin-react@4.7.0` does not support Vite 8, which this project already ran), so vitest 4 is used with `--legacy-peer-deps` — and three guards had to be written and two discarded for false positives before one held.
- **Filtering is now truthful under a day filter.** Four surfaces derived the same answers independently and disagreed: the balance hero computed `opening + income − cash` and ignored credit, debt payments, savings and transfers; the graph skipped debt payments entirely when a filter was set, so it never reconciled with the card; the plan tint compared a month total against a month balance; and the savings history showed the whole month. All four now read one `scopeMonth()` that composes the already-tested helpers, and with no filter it returns the server's stored figure untouched, so the month view is unchanged by construction. **The hero number is now lower in a day view than it used to be, because it is truthful.**
- **Three pre-existing bugs fell out of that work.** The 7-day window started at 23:59:59 of its first day, silently dropping that whole day — a week-long view showed one day. `creditPurchasesAsOf` omitted the backend's `debt_id` filter, double counting a debt's charges as global credit. And `rangeHelpers` had to be extracted out of the `Dashboard` page at all, because a function living in a page cannot be imported without dragging React along, which is why none of this was testable before.
- **A real financial export was found committed to the repository.** `database/data/september.private.json` was tracked from the first commit and had reached `origin/main`. It is now untracked and ignored, and the ignore rule explains why, but the file remains recoverable from history and from any existing clone; see Privacy above.

### alpha 0.5.1 — Unified App Header

- **There was never one header.** `DashboardHeader` was imported by `Dashboard.jsx` and nothing else, so Savings, Análisis and Configuración each hand-rolled a second header into the layout's header slot: four headers, four gutter conventions (`px-3` against the pages' `px-4`, plus a second `px-4` on two of them), and two title sizes that jumped as you navigated. All four screens now render `AppHeader`, and the gutter belongs to the layout alone.
- **The view switcher was invisible on the one device that needed it.** The old pill carried `hidden sm:inline` on the view name, so on a phone — where the `title` tooltip never appears and an icon cannot say which of the three dashboards you are in — you got a bare icon, on the exact case the code comment said the name existed to solve. It is now a full-width segmented control, visible at every width, and it doubles as the swipe affordance: the three dashboards were a swipe with no other sign they were swipeable.
- **Four header buttons became two.** A currency pill, plus an overflow menu holding the theme and settings. The currency switch keeps its "moves TO" semantics, because a switch labelled with the currency you are already in reads as a no-op.
- **The theme is reachable from every screen now.** It was `useState` inside `Dashboard.jsx`, so the other three headers simply had no theme control. It is `useTheme`, alongside the other app-wide display preference that already lived in `localStorage`.
- **The title is a real `<h1>` on every screen.** Three pages used an `<h2>` as their page title, the dashboard had no heading at all, and Análisis rendered a second `<h1>` inside its own panel. That panel's back link moved up into the header too, so every screen has its way out in the same place; the month it was opened for rides along as the header subtitle.
- **"Ir a hoy" no longer shifts the layout.** It was mounted and unmounted with `isNotToday`, shoving the title sideways every time the month changed. It stays in place, dimmed and disabled.
- **The overflow menu is a keyboard widget.** Arrow keys walk its rows, opening lands focus on the first one, and Escape or the Android back button closes it and returns focus to the trigger. All three dismissal paths already existed but were written out at each call site; they are `useMenuDismiss`, which wraps the back-button guard that was added for the dropdowns and dialogs.
- **The shell gaps, closed.** `env(safe-area-inset-bottom)` (only the top inset was handled, so the Android home indicator could overlap content), a `theme-color` meta that tracks the light/dark toggle, `color-scheme`, and a skip link to `<main>`.
- **A test that did not test its claim.** The old suite asserted the view name was in the markup, which `renderToStaticMarkup` emits whether or not CSS hides it — so the phone case the test was written for could fail and the test would stay green. The replacement asserts the active segment carries no `hidden` token, which is the thing that was actually broken. The suite remains static-markup (no jsdom, no testing-library), so focus and arrow-key behaviour is covered by the shared `useMenuDismiss` and the existing back-button suite rather than by a new DOM harness.
- **Version drift, fixed.** `package.json` still said `0.4.1-alpha` while the changelog documented 0.5.0, so Configuración had been showing a version two releases behind to anyone who looked.

## Build and Current-Phase Checks

Prerequisites: PHP 8.3+, Node.js, Composer, Java 17+, Android SDK.

1. **Install Dependencies**:
   ```bash
   composer install
   npm install
   ```
   > **Known peer conflict**: `@vitejs/plugin-react@4.7.0` does not declare support for
   > Vite 8, which this project already runs, so a plain `npm install` fails to resolve
   > the tree. Use `npm install --legacy-peer-deps`. This predates the euro work; vitest
   > 4 is compatible with Vite 8 and is installed the same way.
2. **Environment Setup**:
   ```bash
   cp .env.example .env
   php artisan key:generate
   touch database/database.sqlite
   php artisan migrate --seed
   ```
3. **Build APK**:
   ```bash
   npm run build
   php artisan native:run android
   ```

4. **Run the tests**:
   ```bash
   php artisan test    # backend
   npm test            # frontend: money, rates, ranges, insights, currency rules
   ```
   The frontend suite exists because the money and filtering logic is where the
   subtle bugs live, and PHPUnit cannot reach any of it. Neither suite can render a
   React component, which is why `useCurrencyGuard.test.js` checks components at
   the source level for the two mistakes that ship a white screen.
